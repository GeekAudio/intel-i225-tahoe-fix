## 1. AppleIGC 隔离实验

| 时间 | 本地记录 |
| --- | --- |
| 2026-10-17 至 10-19 | 多次记录 `m->m_flags & M_PKTHDR` / `uipc_mbuf.c:4839`，网络输入线程调用栈；AppleIGC 1.9d2 在加载列表中 |

| 随后约 40 小时 | 43 次 DarkWake，其中 38 次 RTC 唤醒、7 次完整唤醒；没有记录相同网络 panic，有线接口不可用 |

该实验支持“本机停用 AppleIGC 后原网络签名未复发”，不证明全部系统 panic 都已消失，也不能从加载列表直接证明具体 mbuf 损坏过程。[AppleIGC #35](https://github.com/SongXiaoXi/AppleIGC/issues/35) 是相似硬件上的独立报告，不是本机复现或补丁验证。

## 4. 本次纠正的旧结论

| 旧表述 | 发布版表述 |
| --- | --- |
| “I210 kext 完全没有 I225 ID，所以仿冒必需” | 本包已有 I225 personality；带仿冒的组合已验证，去掉仿冒未做对照 |
| “e1000=0 完全禁用 dext，三件套缺一不可” | 这是已测试组合；首次成功启动后仍有 E1000 abort，必要性和作用范围未完整隔离 |
| “I210 名字说明最多只能跑千兆” | 本机协商到千兆；不从名称推断通用上限，也未证明 2.5G 可用 |
| “签名完整验证通过” | 保留 Apple 签名信息；旧资源封套使完整验证报错，忽略资源模式通过 |
| “40 小时证明 I210 长期稳定” | 40 小时属于停用 AppleIGC 的隔离窗口；I210 的长期稳定性需另测 |
| “有线 panic 机制已经源码定案” | 本机对照支持绕开 AppleIGC；没有完成驱动 RX 路径的源码级因果证明 |

## 5. 尚未建立的结论

- 在其他主板、I225 stepping、I226 和其他 macOS build 上是否可用。
- 2.5GbE 协商与实际吞吐、长时间高负载、巨帧和各类 offload 的完整表现。
- 多轮睡眠唤醒后的稳定性、Wake-on-LAN。
- 不注入 `device-id`、不追加 `e1000=0`、或另加 `dk.e1000=0` 的对照结果。
- 使用默认 SIP、AMFI、SecureBootModel 安全策略时的加载情况；测试机另有显卡与无线驱动环境。

本仓库提供可复现的工作组合与回退办法，不把这些未验证项当作已解决。
